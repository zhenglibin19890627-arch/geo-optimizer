## 三、真实监测失败证据（阻塞缺陷 #1）

3 次独立发起 `POST /api/monitor/start`（1 问题 × deepseek），全部 10 秒内 `status=failed`、`error_msg=监测中途出了点意外，请稍后再试一次`、done_calls=0。

服务器错误日志（server2_err.log）：

```
sqlalchemy.exc.OperationalError: (sqlite3.OperationalError) database is locked
[SQL: INSERT INTO api_call_log (engine_code, model, tokens_in, tokens_out, cost_yuan, created_at) VALUES (?, ?, ?, ?, ?, ?)]
```

**根因**：`geo/core/monitor_task.py::_run_monitor_task_inner` 的线程在 `adapter.chat()` 期间持有未提交写事务（task.status 更新 + monitor_round INSERT 已 flush），`log_api_call` 在另一连接写 `api_call_log` → SQLite 写锁冲突（默认 5 秒超时）→ OperationalError 逃逸 → 整轮标记 failed。

**连带影响**：验收标准 #4/#12/#13、完整轮次、报告页真实数据、多轮预警积累、定时自动监测轮全部无法落地。开发自验未发现（自验用 fake adapter，不触发 log_api_call 写库）。

### 5.4 回归新发现缺陷

**缺陷 #8（严重）——预警写库路径 SQLite 锁（缺陷 #1 同类问题残留）**

- 复现：真实触发预警的轮次（本轮 4 轮）均在 `evaluate_round` → `database.set_setting("alert_active_...", True)` 时报 `sqlite3.OperationalError: database is locked`（busy_timeout 15s 超时），异常被 monitor_task 的 `except Exception: traceback.print_exc()` 吞掉，任务仍正常 done
- 根因（测试侧分析）：`evaluate_round` 先 `session.add(Alert)`（外层事务未提交），再经独立连接 `set_setting` 写 settings 表 → SQLite 单写者锁冲突——与缺陷 #1 完全同类（04-11.1 只修了 `adapter.chat` 前的 commit，未覆盖预警写库路径）
- 影响：① 服务器日志 8 次锁异常噪音（每次触发轮卡 15s）；② `alert_active_*` 永不落库 → 连续下降每轮重复 watch、**无法升级 warning**（实测 4 轮 4 条 watch、0 条 warning）；③ 恢复通知（set_setting False）同样失效
- 证据：reg5095_err.log 8 处 traceback（均为 INSERT INTO settings）；隔离库 settings 表无 alert 键；alerts 表 4 条 watch

**缺陷 #9（一般）——报告页轮次下拉仍含取消轮且无状态标识（缺陷 #4 修复不完整）**

- 复现：报告页轮次下拉含取消轮"2026-08-10 00:46 · 10 分"（round 1，cancelled），无"已停止"标识，用户可误读为正常轮次
- 说明：第一轮缺陷 #4 附节已记录"轮次下拉含取消轮"，本轮修复覆盖了监测中心列表/首页/统计口径/预警基线，未覆盖报告页下拉；趋势图/评分已正确排除该轮
